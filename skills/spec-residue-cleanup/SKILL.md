# 清除过程残留

## 目标

在设计收敛后删除讨论过程留下的旧方案和反向提醒，使文档只表达当前有效结构，同时保留真正限制非法行为的门禁。

核心判断：

> 删除后若合法行为边界不变，就是过程残留；删除后会允许非法状态、失败路径或安全越界，就是必要门禁。

## 工作流

1. 先确定当前唯一有效的设计结论和权威来源。
2. 搜索被否决方案、旧术语、旧字段、旧流程、失效计划以及“不要做旧方案”式提醒。
3. 逐项判断其属于历史残留，还是仍约束合法边界的必要门禁。
4. 删除历史替代方案及其解释，不在正式文档中保留讨论轨迹。
5. 将剩余规则改写为当前结构的正向定义；仅在非法边界无法由正向规则清楚表达时保留否定约束。
6. 检查相关章节、示例、硬规则和关联 Spec，清除旧引用、第二真相源、死字段及冲突出口。
7. 查看 diff，并报告删除的残留、保留的必要门禁和仍需人工裁决的歧义。

## 判别规则

### 应删除

- 已被当前方案取代的流程、字段、状态、对象或命名。
- 只为解释“过去为什么没有这样做”而存在的文字。
- 针对已不存在结构的禁止性提示。
- 与权威定义重复、可能形成第二真相源的说明。
- 已失效的迁移计划、临时兼容路径和讨论性 TODO。

### 应保留

- 防止非法状态进入正式流程的门禁。
- 明确安全、授权、原子性、证据充分性或失败归因边界的约束。
- 无法从正向结构唯一推导出的排除条件。
- 为兼容仍在运行的历史数据而实际生效的规则。

## 编辑原则

- 先确认现行规则，再删除残留；不得用搜索命中直接批量删除。
- 优先删除概念、字段、状态和分支，不以压缩语言替代结构清理。
- 保持定义、正向规则、边界、触发条件和失败路径完整可读。
- 不新增“废弃方案清单”或类似持久化历史区。
- 若无法判断某条否定规则是否仍是门禁，保留原文并明确列为待裁决项。

## 验收

清理完成后应满足：

- 文档只存在一个现行方案和一个权威定义。
- 旧术语、旧字段、旧流程及其引用均已消失。
- 必要门禁仍能阻止原本禁止的非法状态。
- 示例、流程图和数据结构与正文一致。
- diff 只改变过程残留及其关联引用，不改变未授权的业务边界。
