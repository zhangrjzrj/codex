# Commit Cleanup

## Purpose

Use this skill as the final archival step after a task is implemented, tested, reviewed, or otherwise ready to be committed.

Do not treat this as a code review skill. This skill decides file ownership, commit grouping, minimal verification, and workspace cleanliness.

## Operating Rule

Apply this policy:

```text
Definitely should commit -> commit it with scoped paths.
Definitely should not commit -> leave out, move to ignored evidence/runtime location only when clearly safe, or report.
Uncertain ownership or risk -> do not commit; report exactly why.
```

Never use `git add .`, `git commit -a`, broad `git reset`, or destructive cleanup. Preserve unrelated user changes.

## Workflow

1. Inspect repository state.

Use read-only commands first:

```powershell
git status --short --branch
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
```

For multi-repo work, inspect every relevant repo separately. In app/backend projects, check both frontend and backend when the user asks about "前后端".

2. Classify files.

Classify each changed or new file:

```text
commit candidates:
  source code, tests, docs, schemas/contracts, migrations, seed/fixture data explicitly meant for the repo

usually exclude:
  logs, screenshots, dumps, caches, build output, generated temporary files, local credentials, account/login state, runtime learning data

needs explicit caution:
  data files, config files, knowledge graphs, generated code, lockfiles, large binaries, files outside the task scope, pre-existing dirty changes
```

Read project-local rules before deciding: `AGENTS.md`, `.gitignore`, package scripts, docs, and recent task context. A tracked fixture can be commit-worthy; runtime data is not.

3. Determine commit groups.

Group by semantic intent, not by file type alone:

```text
mechanism/code fix
tests for that fix
protocol/schema boundary
documentation/test-case update
revert or cleanup correction
```

Prefer one cohesive commit when code and tests prove the same change. Split when changes are independent or one group is a correction/cleanup.

4. Run minimal gates.

Run only gates relevant to the commit candidates. Do not rerun expensive E2E unless the commit boundary changed in a way that invalidates prior evidence.

Typical gates:

```text
JS/TS: node --check, npm verify/test scripts relevant to changed files
PHP: php -l, focused PHP tests, architecture gate when lifecycle/boundary code changed
JSON: parse once with Node/Python
YAML: parse or project validator
skills: quick_validate.py <skill-dir>, plus language checks for included scripts
ignore/runtime boundary: git check-ignore and any boundary verifier
docs only: usually no code gate unless the repo has a doc validator
```

If a gate fails, stop committing that group, explain the failure, and either fix the root cause if in scope or report it.

5. Commit scoped paths.

Use scoped commits:

```powershell
git commit --only path1 path2 -m "中文提交标题"
```

For new files, stage only those files first:

```powershell
git add -- path/to/new-file
git commit --only path/to/new-file path/to/modified-file -m "中文提交标题"
```

Do not stage or unstage unrelated files. Do not include ignored runtime artifacts.

6. Verify each commit.

After every commit, inspect:

```powershell
git show --stat --name-only HEAD
git status --short --branch
```

Confirm the commit contains only intended files.

7. Handle leftovers.

If changes remain, classify them:

```text
left intentionally: unrelated user changes, uncertain data/config, external work in progress
should be ignored: runtime evidence/data generated by the task
should be cleaned: only safe temporary artifacts created by the agent and not needed
blocked: requires user decision
```

Report leftovers without committing them.

8. Final answer.

Report concisely:

```text
commits made
files included per commit
verification run
remaining changes, if any, and why
whether each relevant workspace is clean
```

When the user asks only "收尾干净了吗", skip explanation and answer the cleanliness state directly.

## Escalation Rules

Ask or stop before committing when:

```text
the changed file is a runtime data/knowledge artifact and the repo policy is unclear
the diff contains credentials, phone numbers, tokens, login state, or private account data
the commit depends on uncommitted files that you do not plan to include
the working tree contains pre-existing dirty changes in the same files
the user explicitly asked not to commit
```

If the user has explicitly asked "提交应该提交的部分", commit the clear commit candidates and leave uncertain items uncommitted with a short explanation.

## Quality Bar

The final state is successful when:

```text
all intended changes are committed in coherent groups
runtime/generated/local artifacts are not committed
minimal gates passed or failures are reported
staged area is empty
working tree is clean, or every remaining item is explained
```
