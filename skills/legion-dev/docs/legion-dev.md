# 军团式开发准则（Legion Dev）

## 一句话原则
先把“怎么验收/怎么拦错（门禁）”谈清楚，再开始干活。

> 适用范围：任何存在明确验收点/前置门禁、会改分支指针（rebase/reset/cherry-pick）、或要求“baseline 语义不变”的任务。

## 铁律（最高优先级）
只有足够小的步伐，才能确保稳定坚实、质量可靠；同时把上下文压到足够小，才能确保准确性与质量。

---

## 核心流程（强约束）
1. **AI 先交“执行卡”**（只写计划与门禁，不改代码、不跑高风险命令）
2. **人确认执行卡**（只确认意图/边界/门禁/例外，不逐条盯命令）
3. **按步骤执行**（每一步必须产出门禁证据）
4. **门禁不过就停**（不得进入下一步；需要例外必须重新确认）

---

## 硬触发表（强制进入军团流程）
只要用户意图命中任一条，就必须先输出执行卡并等人确认（未确认前，不执行高风险命令）：
- 改指针类：`rebase` / `reset` / `cherry-pick` / “对齐到某个 commit” / “回退一串提交”
- 高风险批量变更：大范围重构/清理/替换、跨模块联动修改
- 强验收诉求：“闭环做到通过” / “门禁” / “执行卡” / “baseline 语义不变”

## 协同边界与记录规则（避免跑题与混写）
### 本线范围（In Scope）
- 编排协议（Orchestration Protocol）
- 任务生命周期（拆解/并行/汇总/验收）
- 证据门禁（Gates）与审计报告模板
- 自动化脚本与可复用的执行卡模板

### 本线范围外（Out of Scope）
- 具体业务问题本身的对错争论（除非它被明确列入本次执行卡的验收项）
- 与当前主线无关的临时排查细节（应分流到独立 thread）

### 分流原则（Topic Split）
- 一旦出现明显“另一个业务主题”，立刻新开一个 thread 记录，不要污染军团式开发主线。
- 军团式开发主线只保留“流程/门禁/协同机制”的决策与准则。

---

## 角色分工（4+1，降上下文长度）
目标：让每个角色只看“最小证据包”，减少误解与幻觉扩散。

### 必备 4 角色
- **编排者（Orchestrator）**：把目标拆成“可执行步骤 + 每步门禁”，并负责分流与总汇报。
- **开发者（Developer）**：按单步任务实现改动，提交变更摘要，不负责放行裁决。
- **测试者（Tester）**：产出门禁证据（测试/快照/指标/对比）并给 PASS/FAIL，不参与需求争论。
- **审阅者（Reviewer）**：基于“变更摘要 + 门禁证据”做放行/驳回，关注边界与风险。

### 可选 +1（早期可并入编排者）
- **记录员（Scribe）**：把每步结论与证据摘要落盘到 `.codex-memory/`，并维护主题分流。

### 最小证据包（交接工件，强制短）
每一步都用同一格式交接，避免把整段对话当上下文：
- Step 目标：1 句
- 变更边界：2–5 条（允许改/禁止改）
- 本步改动摘要：3–8 条要点（含关键文件路径）
- 验收标准（本步门禁）：必须可判定的 PASS/FAIL（写清楚“证据是什么、阈值是什么”）
- 门禁证据：只贴关键行（命令输出/测试结论/快照对比/指标数值）
- 裁决：PASS/FAIL + 下一步入口（或失败处理）

---

## 小步闭环协议（强约束）
每一步都必须带**明确、清晰、可执行**的验收标准（门禁），以小步闭环前进。

### 闭环总图
```text
Orchestrator（执行卡/验收标准/派单）
-> Developer（单步实现 + 变更摘要）
-> Tester（按验收标准产出证据 PASS/FAIL）
-> Reviewer（基于摘要+证据 放行/驳回）
-> Orchestrator（更新计划/标准/例外，进入下一步或结束）
```

### 强制规则
- **没有验收标准就不允许开始执行**（先补齐执行卡与门禁）。
- **未通过当前步验收标准，不得进入下一步**（FAIL 必须回到本步或重写方案）。
- 验收标准必须二值化：明确 PASS/FAIL，不接受“看起来差不多”。
- 验收标准要写到“证据层”：测试/快照/对比/指标阈值/命令输出的关键断言。

---

## 执行卡模板（AI 必须按此输出）
### 1) 目标（Goal）
- 本次要达成什么（1 句）

### 2) 变更边界（Boundary）
- 允许改什么 / 禁止改什么（2–5 条）

### 3) 步骤（Steps）
- 3–7 步，每步只做一件事

### 4) 每步门禁（Gates）
对每一步都要写清：
- **证据**：用什么证据验证（命令输出/测试/对比/指标）
- **通过条件**：PASS 的判定标准（必须可二值判断）
- **失败处理**：FAIL 怎么处理（回到哪一步、换方案、或申请例外）

### 5) 风险点（Risks）
- 最容易翻车的 3 个点 + 预防动作

### 6) 例外（Exceptions）
- 哪些情况可以放行（必须显式列出）
- 放行需要谁确认（默认：人确认）

---

## 门禁设计原则（“硬”但不写死）
### A. 裁决要硬
- 门禁必须落到 **PASS/FAIL 的断言**，避免“看起来差不多”。
- AI 可以解释与建议，但 **不能当裁判**；裁判是脚本/CI 或者明确的人工确认动作。

### B. 输入要灵活
门禁不写死在规则里，写死在“本次执行卡的参数”里：
- 目标分支/基线点/提交范围/允许例外等，均由执行卡声明。

### C. 证据优先
“baseline 语义不变”不是口号，必须对应证据：
- 单测/集成/E2E
- golden/快照对比（输出、渲染、关键日志、协议响应）
- 契约检查（API/ABI/schema/配置兼容）
- 指标预算（性能/内存/耗时阈值）

---

## 证据包契约（最小可审计产物）
默认证据包落在当前项目工作目录（不是全局目录）：
- `.codex-memory/artifacts/legion/YYYYMMDD-HHMMSS-<topic>/`

必选文件（最小契约）：
- `execution_card.md`：确认后的执行卡（含 Gate 定义）
- `steps/step-01.md` …：每步一份（目标/边界/命令/输出摘要/PASS|FAIL/下一步）
- `result.md`：最终结论 + 未完成项 + 下一步

可选文件（自由扩展）：
- `logs/`：测试日志、关键输出
- `diff/`：range-diff/patch-id 输出
- `screenshots/`：需要人工判读的证据

强制写法：
- 每步必须出现明确的 `PASS` 或 `FAIL`，不接受“差不多”。

## Gate Cookbook（可复制粘贴的门禁模板）
原则：门禁内容可定制，但门禁写法必须可二值判定（PASS/FAIL），且要写清“证据/通过条件/失败处理”。

### 1) 工作区与暂存区门禁（默认保护 staged）
证据（命令）：
- `git status -sb`
- `git diff --name-only --cached`

PASS：
- 暂存区为空（默认不允许动 staged；如需例外必须在执行卡里写明并经人确认）
- 工作区是否允许 dirty 由执行卡声明

FAIL 处理：
- 立即停止；先决定 stash/丢弃/保留，且写进执行卡的 Exceptions

### 2) 分支/HEAD 断言门禁
证据（命令）：
- `git rev-parse --abbrev-ref HEAD`
- `git rev-parse HEAD`

PASS：
- 分支名与 HEAD hash 命中执行卡声明

FAIL 处理：
- 立即停止；回到“执行卡确认”，纠正目标分支/目标基线

### 3) 提交集合一致性（防漏 pick / 误 pick）
证据（命令）：
- `git log --oneline <base>..HEAD`

PASS：
- 提交列表与执行卡的“预期提交集合”一致

FAIL 处理：
- 立即停止；补 pick 或撤销误 pick，再重跑本门禁

### 4) 等价性检查（range-diff）
证据（命令）：
- `git range-diff <upstream>...HEAD`

PASS：
- 无非预期差异（允许差异必须在执行卡 Exceptions 里写明）

FAIL 处理：
- 立即停止；进入冲突复盘或申请例外

### 5) 等价性检查（patch-id，适合单提交/小集合）
证据（命令）：
- `git show <commit> | git patch-id`

PASS：
- patch-id 与预期一致（或差异在 Exceptions 中被允许）

FAIL 处理：
- 立即停止；重新确认目标提交范围/来源

### 6) 隔离执行（降低爆炸半径）
建议流程：
- 风险操作（rebase/cherry-pick/大清理）优先在临时 worktree/临时分支上执行，验证通过再晋升到目标分支。

PASS：
- 隔离区门禁全部通过后，才允许晋升/合回

FAIL 处理：
- 丢弃隔离区结果，不污染主线；回到执行卡调整方案

## 常见场景：推荐门禁清单（可直接拷到执行卡里）
### 1) Rebase / 指针类操作（形变风险）
强烈建议门禁包含：
- 当前分支是否为预期目标分支
- rebase 前后：是否 **丢提交/多提交**
- 与目标基线的祖先关系是否正确（避免在错基线上重写历史）
- 工作区是否干净（避免夹带未提交改动）
- 冲突解决是否产生额外行为变化（对应测试/快照证据）

### 2) Cherry-pick（漏 pick / 误 pick 风险）
强烈建议门禁包含：
- 本次要引入的提交集合（范围或列表）与实际落地集合一致
- 必要时做内容等价对比（例如范围差异对比，而不只看 hash）
- 关键用例/测试必须通过

### 3) Baseline 语义不变（语义风险）
执行卡必须写清：
- “语义不变”到底指什么（输出/帧/协议/指标）
- 哪些证据算通过（测试集、快照对比范围、预算阈值）
- 允许的变化（版本号、时间戳、某目录生成物等）

---

## 停止条件（强约束）
- 任一步门禁 FAIL：**立即停止**，不得继续下一步。
- 发现执行卡缺项（目标不清/边界/门禁不可判定）：**回到“执行卡确认”**。
- 需要例外放行：**更新执行卡并重新确认**。

---

## 失败后的“掉头”准则（强约束）
这条是为了消除你担心的“AI 没有人类思路会走死胡同”：军团化不要求第一版路线完美，但要求**证据否定就必须掉头**。

### 1) 证据否定即掉头（MUST）
当本轮门禁/证据已经明确否定当前假设（FAIL），必须：
- 先落盘：失败证据 + 最小结论（排除了什么）+ 下一条可验证的新假设
- 再切换路线进入下一轮（而不是继续沿错误方向加码实现）

### 2) 撞墙 ≠ 立刻交人（MUST）
撞墙后默认先“掉头再试”，只有在确实**无路可走/需要拍板**时才交接给人类。

触发“人类介入/交接决策点”的条件（建议满足其一即可）：
- 连续 2–3 轮都拿不到新的区分性证据（新信息为 0，只是在重复）
- 需要业务拍板/权限/外部资源，AI 无法获取或无法替代决策
- 风险升高（可能影响主干/发布/数据安全）必须人类确认

## 解决问题的默认思路（强约束）
目的：让“找问题”变成**证据驱动的算法**，而不是大模型随意猜一个方向。

### 1) 优先逆向定位：从问题点反推（MUST）
不猜；从“报错点/异常点/表现点”出发，反向补日志/抓证据，沿调用链/数据链线性回溯，直到找到**第一个**引入异常的源头。

### 2) 逆向走不通时再二分：用证据做 A/B 互斥分叉（MUST）
当无法直接从问题点追到源头（链路断、黑盒、噪声大），再把问题切成两种互斥可能 A/B：
- 每一轮只选择一个“能把 A/B 分开”的证据点（门禁）
- 依据证据 PASS/FAIL 选择下一半
- 多轮二分把范围快速收敛（本质是 log2(N) 次分叉）

### 3) 禁止无证据猜路线（MUST）
任何方向性结论必须绑定门禁证据；没有证据时，只允许输出：
- 假设列表（A/B/…）
- 下一步要补的最小证据（最短路径拿到“决定性证据”）
